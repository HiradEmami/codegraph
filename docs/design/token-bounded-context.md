# Exact token-bounded explore packets

Implemented for the Pelagion fork on 2026-09-26. This is an opt-in output contract
for `codegraph_explore` and `codegraph explore`. Existing Markdown exploration and
its adaptive character budgets remain the default.

## Request

MCP arguments:

```json
{
  "query": "video_assistant transcribe execute_transcription",
  "tokenBudget": { "maxTokens": 2000, "encoding": "o200k_base" }
}
```

CLI:

```shell
codegraph explore "video_assistant transcribe" --max-tokens 2000 --tokenizer o200k_base
```

Both `maxTokens` and `encoding` are required when a budget is requested.
`maxTokens` is an integer from 1 to 1,000,000. Only `o200k_base` and `cl100k_base`
are supported. Model names and unknown tokenizer names are rejected; there is no
fallback to a character estimate or an inferred Codex model tokenizer.

The CLI emits exactly the JSON packet text, without an extra newline. MCP returns
the same JSON as one text content item. Existing `context` command behavior is
unchanged; these flags belong to `explore`.

## What the cap covers

The entire compact JSON packet is encoded with the selected tokenizer. The cap
includes evidence IDs, source paths/ranges, source text, notices, provenance,
query/project identity, and omission/deduplication metadata. It excludes the MCP
envelope, host message framing, the rest of the prompt, and output generated by
the model. It is not a billing-token count or a claim about a private tokenizer.

The packet identifies `js-tiktoken`, the installed package version, the selected
encoding, and `measurement: "exact-encoding"`. `model` is explicitly `null`.
Source strings that resemble special tokens are encoded as ordinary literal
text, not as tokenizer control tokens.

The TypeScript API exports `buildBoundedContextPacket`, `countContextTokens`,
`parseContextTokenBudget`, their types, and `ContextBudgetError` from the package
entry point. The builder returns `{packet, text, tokenCount}`. `tokenCount` counts
the exact returned `text`. It is deliberately outside the serialized packet,
avoiding a self-referential count that changes when its own digits are encoded.

## Packet contract

The packet has `schemaVersion: 1` and the following fields:

| Field | Meaning |
| --- | --- |
| `scope` | `selected-explore-evidence`: the existing exploration renderer already selected candidates; this is not a whole-repository completeness claim. |
| `projectRoot`, `query` | Resolved source repository and normalized query when available from an exploration emission. Generic guidance may have neither. |
| `tokenizer` | Encoding, implementation/version, exact-count scope, excluded framing and no inferred model. |
| `maxTokens` | Requested successful-packet cap. |
| `notices` | Required freshness/worktree warnings, retained before source selection. |
| `evidence` | Ordered source spans or contextual relationship/guidance text. Each has a stable SHA-256 identity. |
| `omitted.evidenceItems` | Candidate chunks omitted wholly or partly by this additional budget. |
| `omitted.sourceLines` | Unique candidate source lines not delivered by this budget. |
| `deduplicated.sourceLines` | Duplicate source locations removed inside this packet. |
| `deduplicated.contextItems` | Identical contextual items removed inside this packet. |
| `truncated` | Some selected candidate evidence did not fit. Even `false` does not mean the entire repository or requested behavior was covered. |

Source evidence has `kind: "source"`, a project-relative `path`, inclusive
`startLine`/`endLine`, `text`, and a file fingerprint when provided by exploration.
The text contains complete source lines without display line-number prefixes.
UTF-8 text, Unicode and CRLF line endings are preserved. A span can contain a
partial function; the packet promises complete lines, not complete functions.
Context evidence has `kind: "context"` and `text`; it does not acquire invented
source ranges or turn a heuristic graph edge into proven resolution.

## Selection, deduplication and omission

1. Exploration performs its existing relevance selection and character limits.
2. Numbered source is converted to source spans against the actual emitted file
   and range inventory. Its pre-budget completeness claims are discarded.
3. Required top-level and inline freshness/worktree warnings enter the envelope
   first. The budget cannot silently remove them to make source fit.
4. Source spans retain exploration relevance order; contextual graph prose
   follows. Spans are divided into manageable chunks of up to 40 lines, with a
   3,000-character chunk target. A single long line stays indivisible.
5. Deduplication uses source path, line number, file fingerprint and line text.
   Overlapping unchanged spans collapse. Identical code at another location, or
   changed source at the same location, remains distinct. Context duplicates use
   a content hash. The process is deterministic and leaves caller inputs intact.
6. Every admission is measured as a complete serialized packet. A chunk that
   does not fit may contribute a measured prefix of complete lines. A line that
   cannot fit is omitted, and smaller later candidates may still fit.
7. The final serialized packet is measured again before delivery.

This v1 selector does not optimize graph connectivity, fair shares between files,
or answer sufficiency. A small cap can omit relevant methods or relationship
explanations. Use the omission fields and an appropriate budget; lower output
size alone does not establish a better development result.

Budgeted packets are self-contained and ignore the optional legacy cross-call
dedup setting. They never depend on source from a prior turn surviving compaction
or being visible to another agent. Only actually delivered source ranges enter
session history. The cap is applied after main-thread freshness notices, including
when source retrieval ran in a query worker. Legacy unbudgeted session behavior
is unchanged.

## Errors and resource bounds

Invalid budget requests produce `isError: true` and a small JSON error containing
`schemaVersion`, `error.code` and `error.message`. Expected codes are
`invalid_token_budget`, `budget_too_small` and `invalid_evidence`. Error messages do
not echo arbitrary supplied tokenizer names or source text.

A cap too small for mandatory metadata/notices returns `budget_too_small`; it
does not return an oversized successful packet or pretend an empty packet fit.
Protocol errors are outside the successful-packet cap: a one-token cap cannot
contain a meaningful JSON error envelope. Existing unrelated errors, such as
path-security refusals or CLI startup failures, retain their prior error shape.

Successful no-match and unindexed-project guidance is budgeted too, including the
unindexed exception path used with session history. No source is invented for
these responses. An insufficient budget instead returns the explicit error.

The generic builder accepts at most 10,000 candidate items and 512,000 characters
across candidate text, notices and query/project identity. It keeps at most two
tokenizer instances, one for each supported encoding. The chosen encoding's
bundled ranks load on first use; ordinary unbudgeted calls load no tokenizer ranks
and no ranks are downloaded at query time.

The pinned runtime dependency is `js-tiktoken` 1.0.21 (MIT), with `base64-js` 1.5.1
as its added transitive dependency. Its npm package has an approximately 21.4 MiB
unpacked footprint. Lazy loading avoids an ordinary-query startup tax but does
not make the selected encoder's memory or initialization cost disappear.

## Verification and limits

Focused tests cover both encodings, multilingual and special-token-like source,
metadata-inclusive limits, overlapping source dedup, differing source versions,
whole-line truncation, impossible budgets, malformed requests, source attribution
including CRLF, required notices, no-match/unindexed guidance, session history,
real CLI output, and an actual query worker. Existing explore output, cross-call
dedup and session tests also pass.

At the final handoff, 113 distinct tests have passing evidence: 28 packet/handler,
7 built CLI/worker, and 78 existing compatibility/session tests. These were focused
runs, not a complete repository suite. TypeScript compilation and asset copying
passed; no UI, native Rust, release bundle or cross-platform build was performed.

The three earlier Pelagion evaluation queries were run on the same existing
snapshot/index with no reindex, using `o200k_base` and a 2,000-token cap:

| Query | Original characters | Original tokens | Packet tokens | Omitted source lines |
| --- | ---: | ---: | ---: | ---: |
| Video transcription | 23,905 | 5,101 | 1,985 | 235 |
| PDF inspection | 9,838 | 2,324 | 1,987 | 16 |
| Subtitle operations | 19,721 | 4,177 | 1,997 | 189 |

All three packets report truncation. They contained no duplicate source/context
items, so the measured reduction came from selection and omission, not duplicate
removal. No Codex completion-quality or billing savings experiment was run.

In that Windows/Node 24.12.0 sample, the first encoder-bearing call took 565 ms;
subsequent budgeted retrievals took 79–204 ms. Unbudgeted samples took 41–160 ms.
These are small sequential observations, not latency guarantees or a controlled
throughput comparison. Process RSS increased from 188,510,208 to 419,987,456 bytes
across the run; that is neither peak memory nor isolated tokenizer memory. Only
the requested `o200k_base` rank module loaded. The initial TypeScript-plus-assets
build took 7.19 seconds on this machine.

Detailed receipts live in the sibling `codegraph-evaluation/repair-evidence/`
directory as `context-budget-*`; the supervisor's combined repair report links
them. That evaluation directory is not part of the published npm package.
